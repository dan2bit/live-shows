| [#231](https://github.com/dan2bit/live-shows/issues/231) | `spotify_cache.py` decomposes portrait maintenance by price tag instead of a quarterly full-roster sweep: `--heal-only` (modifier for `--refresh-images`) restricts the sweep to entries never stamped by a successful pull — the single-digit empty-at-resolve heal set, the only non-cosmetic function — and `--check-image-rot` HEAD-checks every cached portrait URL against the public CDN (unmetered, outside `--limit`), re-fetching via the metered API only URLs answering 404/410. | [#245](https://github.com/dan2bit/live-shows/issues/245) | The staged bootleg-upload toolchain (`youtube_upload_show.py`, `yt_clipscan.py`, `yt_common.py`): script-side resumable `videos.insert` replacing the manual Studio-first upload, with a per-show manifest as the durable artifact between stages — YouTube's Content ID scan finishes long after upload and the correction pass is human, so no single run can straddle either; a blank `Video ID` doubles as the upload work queue, so an interrupted or deliberately split upload resumes for free. Also drove the layered song-ID architecture validated across two shows: Content-ID matches as trustworthy fixed points bound to source clips by duration to <1s; setlist.fm for ordering and the candidate pool; lyric hydration resolving within that pool from artist-scoped sources, where the absence of any indexed lyric is itself the unreleased-song signal; capture timestamps for set-boundary detection and fragment flags but explicitly NOT for setlist position, since sets are often filmed out of order and lyric/Content-ID evidence must override the positional guess. Content-ID blind spots have two distinct causes — unreleased songs (no fingerprint can exist) and live covers (the fingerprint does not match the performance) — and both route to lyric/manual ID. The reverse-index upload-order idea was tested and dropped: it produced reverse-chronological order on one show and scrambled order on another, so upload/list order carries no sequencing signal and capture timestamps remain the sole authoritative ordering source. The fragment threshold sits at 60s, above the longest observed real fragment (54s) rather than at the low end of the 30-45s range, because the errors are asymmetric: a wrongly flagged keeper costs one manifest edit, a missed fragment ships a published false start. Segment boundaries require both an absolute gap floor and a multiple of the night's own median gap, so a tightly-filmed night's banter does not read as a set change. |
| [#250](https://github.com/dan2bit/live-shows/issues/250) | The `State` column on `venues.tsv`, replacing per-consumer address parsing. Two divergent regexes had grown for the same job in `youtube_create_playlists.py` and `yt_common.py`, disagreeing on real inputs; both now read the column and keep their parse only as a blank-cell fallback, so a hand-added row without a `State` degrades exactly as before, and a row with a `State` but no address at all (the skeleton venues seeded from show history) resolves for the first time. The same rewrite padded every row to full width, retiring the ragged-tail hazard (truncated trailing columns made `DictReader` yield `None`, forcing `(x or "")` on every reader), and surfaced two long-misaligned DEFUNCT rows whose values sat one and two columns left of home — invisible to width checks because surplus blanks before `State` kept the field count correct. Investigation confirmed the divergence was confined to those two Python scripts: `app.js` and `check_box_office.py` consume only `Venue Name` plus their own display/capability columns and first-comma-truncate away the address text entirely. Alongside, `youtube_create_playlists.py`'s data paths were anchored to the script's own location — its bare cwd-relative names predated the repo reorganization and matched no real directory, so venue and history lookups had been silently degrading. |
